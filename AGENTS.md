# AGENTS.md - Lumina

Operating instructions for coding agents in this repository.

## Working Rules

- Act as a senior engineer: precise, minimal-diff, and evidence-based. Do not add teaching commentary.
- Inspect `git status --short --branch`, the current diff, and the relevant executable config before editing. Task branches may lag `dev`.
- The checked-out repository overrides this file. If they disagree, state the discrepancy and follow the repository.
- Preserve unrelated dirty changes. Never reset, clean, or rewrite work you did not create.
- Verify commands before claiming success. Never invent files, endpoints, checks, or passing results.

## Current Architecture

- Python is pinned to 3.12. Backend code uses FastAPI, Pydantic 2, and SQLAlchemy 2 typed declarative models.
- `backend/app/config.py` owns application settings. `backend/app/database_config.py` reads the database-only subset for Alembic. `.env` is not loaded automatically; launchers must inject configuration. Do not add environment reads elsewhere. Settings are frozen and import-cached.
- `DEPLOYMENT_MODE=self_hosted` defaults to SQLite and local paths. Hosted staging requires PostgreSQL and is exercised by a pinned live CI service; hosted production is qualified only with `STORAGE_BACKEND=s3` plus PostgreSQL, and fails at startup otherwise.
- `backend/app/database.py` creates SQLite parent directories outside production and enables `PRAGMA foreign_keys=ON` for every connection. Do not remove the listener; SQLite cascades depend on it.
- `backend/app/models.py` defines the 26-table relational model. `ExamTopicCandidate.course_id` is the same denormalization, held true by a composite foreign key into `generated_outputs`, which carries a unique `(id, course_id)` index so a course-scoped child can reference it. `PastExamQuestion.course_id` is held the same way by a composite foreign key into `uploaded_documents`, because a question belongs to the paper it was printed in rather than to whichever analysis read it. `DocumentChunk.course_id` and `DocumentPage.course_id` are intentional denormalization for course-scoped reads. `ChunkEmbedding` denormalizes `document_id`, `course_id`, and `chunk_index` the same way, held true by a composite foreign key into `document_chunks`.
- Keep DB `ondelete="CASCADE"` and ORM `cascade="all, delete-orphan", passive_deletes=True` together. `User -> Role` deliberately does not cascade.
- Root `routes/`, `schemas/`, `services/`, and `utils/` belong to the FastAPI layer. Do not move them under `backend/app/` without an explicit team decision.
- User, course, document, and processing services persist through SQLAlchemy sessions; do not reintroduce process-local stores.
- `main:app` includes auth, course, progress, admin, user, profile knowledge, document, study guide, generated output, exam mode, quiz, flashcard, AI tutor, course Q&A, conversation, and prompt generator routers.
- `GET /api/progress` is the dashboard's one-request read: one summary per owned, non-deleted course, derived at read time from quiz attempts, generated outputs, and conversations rather than from the materialized `progress` row. It is owner-scoped by an `owner_id` predicate rather than by `utils/authorization.py`, so the administrator read-any override deliberately does not apply. A course with no graded attempt reports `average_score` and `completion` as null rather than zero, because zero is a claim the data does not support, and `total_time_spent_seconds` is null rather than zero when no attempt recorded a duration. `services/course_status.py` is the only owner of the course-status rule and both progress reads derive `status` through it, so the bulk read and `GET /api/courses/{id}/progress` can never disagree: `mastered` when the average score, rounded to the whole percentage a client displays, is at or above `MASTERED_THRESHOLD`, else `practiced` once any attempt exists, else `processing` while a document is `uploaded` or `processing`, else `ready` once one is `ready`, else `no_documents`. Furthest-along wins, so uploading into a mastered course never demotes it. A `failed` document counts as neither material nor work in progress and a `deleting` one is a tombstone, so a course whose documents all failed reports `no_documents` — there is nothing to study — which is why the client labels that state for what it is rather than claiming the course is empty. The rounding is not incidental: a card prints `round(average * 100)` beside the badge, so comparing the raw fraction would put `practiced` next to the number 80. The client derives no status of its own; it maps the value to a label and a tone.
- `GET /api/activity` is the cross-course history read: one owner-scoped chronological list, newest first, bounded by `limit`. It has exactly two sources, `generated_outputs` and `quiz_attempts`, and a generated quiz is counted once from `generated_outputs` even though generation also writes a `quizzes` row, so the feed never reports one piece of work twice; a retake is legitimately its own event. Stored generation documents are read permissively, so a row whose JSON no longer parses loses its topic rather than failing the feed. Like `GET /api/progress`, it is scoped by an `owner_id` predicate rather than by `utils/authorization.py`, so the administrator read-any override deliberately does not apply.
- `services/credits.py` is the only module that may modify `users.credits`. Every balance change updates the balance and appends one `credit_transactions` row in the same transaction, so a metered balance always equals the sum of its deltas; the ledger is append-only and corrections are new rows. All seven charge sites (study guide, quiz, flashcard, AI tutor, course Q&A, prompt generator, exam topic analysis) go through `CreditService.charge`/`refund`, and a refund carries a unique `refunds_transaction_id` so a charge can be reversed at most once. `GENERATION_CREDIT_COSTS` is the authoritative price table and is served to clients rather than hardcoded by them; a quiz containing open-ended questions costs 2 because it prepays the AI grading of every attempt, which is why quiz grading charges nothing and can never be skipped for want of credit. A null balance means unmetered, which is how administrators work and what `CREDIT_METERING_ENABLED=false` extends to a whole self-hosted deployment; exemption is never faked with a large number. The monthly grant is lazy rather than scheduled, evaluated when a balance is charged or read and made idempotent by a unique `(user_id, grant_period)`. Administrators move a balance through the single `POST /api/admin/users/{email}/credits`, which takes a signed `delta` and a mandatory `reason` of `admin_grant`, `support_compensation`, or `admin_adjustment`; there is no separate grant or adjust route, no set-balance operation, and a manual change is deliberately unbounded. Those two mechanisms are the only ways out of a zero balance, and a client must offer no other, because there is no purchase path. `GET /api/users/me/credits` is the balance a user interface reads: it alone evaluates the lazy grant, and it returns the policy that explains the balance, reporting nulls when the account is unmetered. A refusal is identified by the `X-Error-Code` header that every AI route now sends beside `detail`, not by the bare status. See `docs/credits.md`.
- `IMPLEMENTED_AI_PROVIDERS` in `backend/app/config.py` is the authoritative provider list, and a test asserts `get_text_generation_provider` constructs every name in it. `openai` and `claude` are recognized but unimplemented and fail at startup for both `AI_PROVIDER` and `AI_FALLBACK_PROVIDERS`, never at request time. `get_text_generation_provider` returns a `ReliableTextGenerationProvider` wrapping the primary and fallbacks; concrete providers return plain text or a JSON object and feature services own prompt construction, schema validation, and persistence. See `docs/ai_providers.md`.
- Course resources are owner-scoped. `utils/authorization.py` is the only course authorization boundary; every course-scoped endpoint must depend on `require_course_access`, `require_course_owner`, or `require_course_deletion` instead of trusting a client `course_id`. Unauthorized or missing courses return `404`, never `403`. Administrators may read any course but write only their own. See `docs/database.md`.
- Document upload validates bytes and writes generated, content-derived keys. Never derive storage keys from client filenames. `storage/base.py` defines the synchronous `Storage` contract plus the canonical portable key generator and key validator shared by both providers. `storage/local.py` stores under `UPLOAD_DIRECTORY` and, because upload creates one directory per document, its `delete` prunes the directories it emptied back up to but never including the root, so removing a source does not leave an empty folder behind for every document ever deleted; pruning is best effort and never fails a deletion that already happened, and S3 needs no equivalent because its keys are flat; `storage/s3.py` stores in an S3-compatible bucket via boto3 with an injectable client (tests fake it; the hosted Compose is the live qualification). `storage/dependencies.py` builds the provider from settings; the readiness probe exercises `check_ready()` on the configured provider.
- Alembic is the only runtime schema-management mechanism. `alembic/` is the sole script directory and all revisions live in `alembic/versions/`; never create or restore a parallel tree such as `migrations/`. The canonical chain is `97d9fd86a3ba -> b6d8f2a4c901 -> d2a7f0c91e35 -> c4e6a8f1b203 -> f7a3c9d2e541 -> a8c4e2f7b913 -> a4fd52f56b91 -> b7e2a9d1c3f4 -> e5c1a7b39d64 -> a1c5e7f9b203 -> c9b3d5e08f27 -> d3f8b21a6c40 -> e4a7b1c90d52 -> f4b18c7a2e60 -> 910e2719d549 -> 2a7c4e9f8b10 -> 7b3e1a9c4d28 -> b2f47c8d0915 -> c8e1f5a9b3d2 -> c8d4a1f39e72 -> f5a7c2d9e104 -> d7f3a2c48e15 -> b9c1d4e7f2a6 -> a3d9e5c17b48 -> e7c1d4a8b203 -> f8b4c2d1e7a3 -> 3e8b1a4c7f20 -> c2a6e9f4d817 -> 784a1eb8fba0 -> d1f6b3a8c724 -> e2b7c94f1a03 -> f3c8d05a2b16 -> a6d3f81c9b47`; add schema changes as descendants and keep one base/head unless an explicit migration design requires otherwise.
- Every AI prompt is a versioned JSON template under `app/prompts/`; no prompt text lives in Python. `services/prompt_loader.py` loads them and `schemas/prompt_template.py` renders them, rejecting an undeclared `{{PLACEHOLDER}}` at load time and an unsupplied one before the provider call. Both checks scan the template body, never the rendered output, because a placeholder appearing inside a variable's value must stay inert; that inertness is the anti-injection guarantee and services render user text and course material last to preserve it. Every template declares `EDUCATION_LEVEL`, `COURSE_TITLE`, `SUBJECT_AREA`, and `MATERIAL_KIND` ahead of its own variables, and `services/prompt_context.py` is the only place that resolves them: course value, then profile value, then a neutral `unspecified` that never stands in for undergraduate. `prompt_generator` is not course-scoped and deliberately gets a user-scoped context with neutral course fields. See `docs/prompt_templates.md`.
- `frontend/` is a React 19 + TypeScript + Vite application with its own npm lockfile and commands. It has no CSS framework, no component library and no state manager; do not add one without an explicit team decision. Server state is owned by `src/lib/query/`, a small in-repo query cache adopted by explicit team decision rather than a third-party library, so there is still no data-fetching dependency: `useQuery` takes a key built only by `src/api/queryKeys.ts` and a fetcher that threads `{ signal }` through the existing `options?: RequestInit` seam, and `useMutation` invalidates by key prefix. Prefix matching is element-wise, never a string match on the serialised key, because `["course",1` is a string prefix of `["course",11,…]` and course 1 must never invalidate course 11. A query distinguishes `status: 'error'` from an empty result, which is what keeps "unavailable is not empty" true; `refetch` is always present so `ErrorState` always has a recovery route. Unmounting does not abort a request — that is what makes StrictMode's double mount a no-op and stops two screens refetching the same course — so `queryCache.clear()` on logout and on `auth:unauthorized` is correctness, not hygiene. The cache is a module singleton reset once in `setupTests.ts`; do not add a provider. It schedules no timers of its own, so it cannot disturb a suite running fake timers. `src/styles/tokens.css` is the single source of colour, type, space, radius, elevation, z-index, breakpoint, and motion, and components consume semantic roles rather than literals, so a hex value in a component file is a defect. Styling is CSS Modules; fonts are self-hosted under `src/assets/fonts` precisely so a self-hosted deployment makes no third-party request. Routes are named for what the screen calls things, so a course lives at `/courses/:id` and the account is four addressable sections under `/account`; the older `/workspaces/` and `/profile` paths survive only as redirects. `src/ui/` holds the primitives and knows nothing about features, `src/app/` holds the shell and routing chrome, `src/features/<domain>/` holds screens, and `src/components/` keeps only the route guard, document rows, and credit chips. There is no page-level global CSS: every styled component owns a `Name.module.css` beside it, and `src/styles/tokenUsage.test.ts` fails the run if a module reads a custom property nothing defines, because an undefined `var()` fails silently. `src/styles/rawValues.test.ts` is the other half of that guarantee: it rejects a colour literal anywhere outside the token file — hex, URL-encoded hex inside a data URI, a named colour, or a colour function carrying no `var(--` — and `DOCUMENTED_EXTERNAL_VALUES` is the only exemption, which needs a reason and fails once it no longer matches the file. The same test forbids `[data-theme]` and `prefers-color-scheme` in a component module, because `ThemeProvider` removes `data-theme` when the preference is `system`, so a component-level dark branch never fires for a viewer on system-dark who never touched the toggle; a theme branch belongs in `tokens.css`, defined in all three blocks. `src/ui/` primitives are imported by module and there is no barrel. `ErrorState` is the only way a failed operation is reported — it wraps `Alert` and takes `onRetry` or `actions`, so a load failure always carries a recovery route, while a plain `Alert` stays correct for a form validation error. `Dialog` is the only modal and `ConfirmDialog` the only destructive confirmation: there is no `window.confirm`, no bespoke backdrop, and no second focus-trap implementation. `IconButton` requires `label` so an icon-only control cannot compile without an accessible name, `AppShell` owns the single `<main>` so a page inside it must not render its own, while `AuthLayout` is a second shell outside it and therefore owns one of its own, and no two controls inside one dialog may answer to the same name, which is why a footer never says Close next to the dismiss control that already does. A disabled control explains itself in visible text rather than a `title`, since a disabled button is neither focusable nor announced. Branch AI failures on the `X-Error-Code` header rather than the status — `describeGenerationError` is the single mapper and `no_relevant_material` and `material_not_indexed` both arrive as 409, so a status branch silently merges a too-narrow topic with an indexing gap that a retry would clear — keep `retrieval_narrowed` and `context_truncated` distinct, read the credit balance only from `GET /api/users/me/credits`, treat a null balance as unmetered by rendering no credit UI at all, and never hardcode a generation price. No screen may show a number the backend cannot produce: a metric that is unavailable is absent, not zero. A quiz attempt reports `graded_count` beside `total_questions`; score is correct out of graded, and an ungraded written answer is counted separately and never as wrong. `setupTests.ts` turns React's duplicate-key, DOM-nesting, `act`, and ARIA warnings into failures, so a green run means the render was clean, and a regression test is only finished once you have watched it fail with the fix reverted. Two guards enforce the honesty rules rather than leaving them to review: `src/features/honesty.test.ts` rejects a success notice in a screen that calls no API and takes no save callback, a nullable metric coalesced to `0`, and a hardcoded stand-in fixture; `src/styles/fadedText.test.ts` rejects an `opacity` in any CSS rule that also sets a `color`, because the palette is picked to clear its contrast ratios and a fade silently blends it below them where only a browser can measure. `frontend/e2e/` is a Playwright suite covering the quiz end to end, the auth routes, and axe over eight screens; it answers its own API calls through `page.route` and serves the built app with `vite preview`, so it depends on nothing outside `frontend/` and needs no deployed stack. Nothing committed may depend on `.user/`, which is a scratch directory that can be deleted at any time. CI runs the suite as the non-blocking `Frontend end-to-end` job. `npm run lint` passing does not mean `npm run build` passes, because the build type-checks tests and the browser specs too. See `docs/frontend_system.md` and `docs/frontend_testing.md`.
- Chunk embeddings and course-isolated semantic retrieval are implemented. `services/vector_store.py` owns durable vector storage behind one interface with two backends chosen by `VECTOR_BACKEND`: pgvector on PostgreSQL, ChromaDB at `CHROMA_PERSIST_DIRECTORY` on SQLite. `services/semantic_retrieval.py` ranks the chunks of one course against a query embedding and resolves them back to chunk text; the course scope is mandatory and never optional. Study guide, quiz, flashcard, AI tutor, and course Q&A read retrieved material through `services/retrieval_material.py`, which applies the `RETRIEVAL_MIN_SIMILARITY` floor above the ranking seam, spends the character budget in similarity order, and emits in corpus order. It never falls back to whole-corpus assembly: a retrieval failure fails the request. Ranking that returns nothing at all is reported as `MaterialNotIndexedError`, separately from a relevance miss, because a course with ready chunks and no vectors is fixed by `python -m workers.embedding_backfill` rather than by a broader topic. `services/retrieval_query.py` turns each request's topic focus or current student question into the query the feature ranks against. See `docs/vector_storage.md`.
- Generated content carries per-claim source citations. `services/retrieval_material.py` heads each supplied passage with a positional key (`[S1] (Lecture 4, p. 12)`) and charges the header against the character budget, so a citing feature reaches slightly less material at the same `*_MATERIAL_MAX_CHARS`; `include_citations` is a required argument so every caller declares intent and flashcards opt out at the seam rather than in a prompt. `services/citations.py` is the only place a key becomes a citation: it drops any key the prompt did not supply, deduplicates by document and page, caps a claim at four, and for Q&A and Tutor also deletes the unresolved marker from the answer text. `ConversationService.format_history` strips markers out of earlier turns, because a stale key resolves against the new turn's map and would name the wrong passage. The document label is derived from `original_file_name` and has `[`, `]`, and newlines removed, since a file name is student-supplied and reaches model-facing text. Citations are stored denormalized on `quiz_questions.citations`, `conversation_messages.citations`, `exam_topic_candidates.citations`, `past_exam_questions.citations`, and inside the study guide's `generated_outputs.content`, so a reopen renders the same sources with no provider call and no join, and a citation survives the deletion of the document it names; for that reason a citation is never a link. Keys, labels, and cited text must never reach logs or `ai_usage_logs` — the drop path logs a count only. See `docs/citations.md`.
- Embeddings are generated in the worker parent process and written inside `complete_job`'s transaction, after the chunk flush and before `ready`. A document must never reach `ready` without one current vector per current chunk. `services/embeddings.py` owns the `EmbeddingProvider` seam, which is separate from `TextGenerationProvider`; `IMPLEMENTED_EMBEDDING_PROVIDERS` is authoritative and unimplemented providers fail at startup. `services/document_embedding.py` owns the failure classification the job state machine consumes.
- `python -m workers.embedding_backfill` reconciles vectors for chunks that predate indexing. It is idempotent and safe to rerun; `--prune-orphans` removes vectors whose chunk is gone.
- Course deletion is unconditional, permanent, and owner-only; there is no soft delete and administrators cannot delete another owner's course. `CourseService.hard_delete_course` is the only deletion path: it tombstones and fences, then removes storage, then vectors, then the row. `courses.is_deleted` means purge pending and is not client-settable. `python -m workers.course_purge` finishes deletions a storage or vector-store failure left unfinished; it is idempotent, `--course-id` scopes it, and `--dry-run` reports without deleting. See `docs/database.md`.
- `services/course_material.py` is the whole-corpus path, now used by the profile-knowledge assembly helper. It bounds the assembled material to a caller-supplied character budget and reports truncation; the ordering and the budget are the contract its tests assert. It is deliberately dumb selection being replaced feature by feature by `services/retrieval_material.py`, so keep authorization, provider calls, validation, and persistence out of both. Neither module reads settings: the calling feature supplies every bound.
- Course Q&A and AI Tutor persist separate typed conversations through `services/conversation.py`. Generation continuation requires the conversation id, current user, course, and type to match; list/detail reads are course-scoped and follow the normal administrator read override. Existing pre-type rows are truthfully backfilled as `course_qa`. Only successful user/assistant pairs are stored, in chronological message order.
- Study guide responses report `retrieval_narrowed` (retrieval chose a subset of the course, the normal case) separately from `context_truncated` (the character budget dropped a chunk retrieval had already selected). Do not collapse them: before retrieval `context_truncated` meant `chunks_used < chunks_available`, which now holds on nearly every request.
- Quiz generation validates the provider's whole response, and checks it against the requested count, allowed question types, and difficulty, before writing anything; the quiz and its questions are then written in one transaction. `quiz_questions.correct_answer` is the authoritative answer document and `options`/`correct_option_index` are a mirror kept populated for the two option-based types. Attempt grading scores multiple choice and true/false by option index, short answers by normalized match against stored accepted variants, and open-ended answers through the provider; an answer the provider could not score is recorded ungraded rather than wrong and never fails the attempt. See `docs/database.md`.
- AI routes must not return exception text. `utils/ai_errors.py` owns the exception-to-response mapping; every public message is a constant and the stable category is logged, never sent.
- `generated_outputs.user_id` and `generated_outputs.model_used` record the requesting user and the model that actually produced the row. `generation_settings` and `generation_context` record the requested options and what retrieval actually produced, as versioned JSON documents written strictly through their Pydantic models and read back permissively so one bad row can never fail a history read. All four are nullable only because legacy rows have no truthful value; they are never backfilled, and every new study guide and quiz row must populate them. `GeneratedOutputService.record` is the single writer, so a feature cannot store attribution its own way.
- `GET /api/courses/{id}/generated-outputs` and `.../generated-outputs/{output_id}` are reads, so administrators may read another owner's history but still cannot generate into their course. An output is always looked up scoped to its parent course, and reading never calls an AI provider.
- Exam Mode turns a course's chosen sources into a ranked, explainable, immutable study plan, and it separates discovery from selection from planning on purpose. Discovery is split by owner rather than by call: an analysis discovers topics, while the questions in a `past_exam` document are transcribed once by the upload worker and belong to that paper forever. `PastExamExtractionService` runs after `complete_job`, reads the whole document in page order through `load_document_material` rather than a retrieval-bounded slice — a paper's last question is not less of a question for ranking lower against a similarity query — and is free, best-effort, and never able to fail an upload: the outcome lands on `uploaded_documents.exam_extraction_status` / `exam_extraction_error_code` and the document still reaches `ready`. A paper still marked `pending` or `failed` gets one more attempt the first time an analysis selects it, which is also how papers uploaded before extraction existed reach the ranking; `succeeded` and `not_configured` are settled and are never retried. An analysis then counts rows that already exist, so a rescan re-reads no paper and two analyses of one paper cannot disagree about what it asks. The two vocabularies meet through `canonical_topic_key` alone, with nothing stored to connect them. Every selected paper counts whether or not its own prose won a place in the retrieved material, because a retrieval budget must not decide what an exam has asked. It reprocesses nothing: `ExamSourceAnalysisService` reads already-`ready` documents through the existing chunks and vectors, narrowed by the new optional `document_ids` filter that runs through `VectorStore.search`, `retrieve_course_chunks`, and `load_retrieved_material`; `course_id` stays mandatory so the filter can only narrow, and an empty selection raises rather than meaning the whole course. Selected documents are validated in one course-scoped query *before* the credit charge, so a cross-course id is a `404` indistinguishable from a missing one and a still-processing document is `source_not_ready` rather than a misleading indexing gap. The student then chooses the exam scope; `all_discovered` selects every candidate with no cutoff, reuses the same analysis, and still reports `manual_review_recommended`. `services/exam_topics.py` and `services/exam_ranking.py` are pure — a test asserts they import no database, provider, or clock — so `rank_topics` is byte-for-byte reproducible from persisted values and a plan can be proved identical twice. The model supplies labels and aliases and is given no field for a score, rank, or ordering; Python supplies identity through `canonical_topic_key`, which is what lets `course_topics.name`, `quiz_questions.topic`, and the model's own wording resolve to one topic, and why nothing references the churning `course_topics.id`. Ranking weighs syllabus emphasis 30, past-exam frequency 25, mastery need 25, and material coverage 20; a signal the course cannot supply is removed and its weight redistributed to integers summing to exactly 100, never scored as zero, because "no past exams were selected" and "this topic never appeared in one" are different facts. An unavailable signal serialises `raw_value` and `normalized_value` as null; an unattempted topic reports a null `mastery_percentage` and a documented neutral prior rather than 0%, so it can neither outrank a topic the student measurably failed nor vanish. The student's explicit priority is an ordering tier above the score rather than a hidden boost, ties break through a chain ending in `topic_key` so the order is total, and every explanation is assembled from constants — no provider is ever called to phrase one, and a model-authored label is never interpolated into a sentence. Analysis charges (`exam_topic_analysis` 1.0, `exam_topic_analysis_rescan` 0.5) and a topic charges once (`exam_topic_unlock` 2.0) — `ExamEntitlementService.ensure_unlocked` buys every artifact of one topic together and bills the first one asked for, keyed by (course, student, topic) with no plan identifier so a regenerated plan is free; it commits on its own, because rolling the unlock back with a failed generation would bill the retry a second time for access the student already paid for. Every per-topic artifact climbs one ladder in `services/exam_artifacts.py` — resolve the plan, assert the topic is one it ranked, unlock, retrieve narrowed to the plan's analysis's own selected documents, generate, validate, persist — so a guide for one topic can never answer from a course the student excluded from their exam scope, and a topic key that is merely well-formed buys nothing. A failure after the unlock calls `ExamEntitlementService.release`, which deletes the row and refunds, so a failed first artifact leaves the student neither charged nor unlocked and the retry is priced as a first purchase. Extraction, ranking, and reopening are free, so `exam_plan` is rate limited but deliberately absent from `GENERATION_CREDIT_COSTS`. A plan's `model_used` is null because Python produced it. Plans are versioned and never rewritten: staleness is recomputed on read from a stored fingerprint, reports sorted reasons, distinguishes `requires_rescan` from `is_stale` so a moved exam date is not a nag, and compares mastery against the fingerprint's own `mastery_user_id` rather than the reader's — otherwise the administrator read override would report every read of an owner's plan as new quiz results. A first plan needs a future `exam_date`; after that the date never gates anything again, because a plan is a study resource and does not expire with its exam. See `docs/database.md`.
- The root `Dockerfile` and `docker-compose.yml` are the supported single-host self-hosted container path. They run one-shot migrations before separate API and worker services as UID/GID 10001 on a shared named volume. `docker-compose.hosted.yml` is the hosted topology: pinned pgvector and MinIO services, a one-shot `minio-init` bucket provisioner, and the same migrate/API/worker roles wired to S3 storage and pgvector. Hosted production config requires `STORAGE_BACKEND=s3`; MinIO itself is gated by the API and worker readiness probes because the MinIO image has no shell.
- AWS frontend delivery is a private, versioned S3 bucket behind CloudFront OAC. The public frontend hostname serves static `current/` content and routes exact `/api` plus `/api/*` paths without caching to a distinct certificate-covered ALB origin hostname; never use a distribution-wide SPA error fallback because it corrupts API errors. `VITE_API_BASE_URL=/api` is the same-origin default. Optional cross-origin builds require exact `CORS_ALLOWED_ORIGINS`, bearer-header auth with credentials disabled, and exposed `X-Error-Code`. The first rollout keeps DNS on the ALB until `current/index.html` is published, then enables `frontend_dns_cutover`. Frontend and backend deploy as one commit-SHA release, and rollback verifies both artifacts before mutation. See `docs/deployment.md`.
- AWS runtime database traffic goes through TLS-only RDS Proxy; the one-shot migrator uses a separate direct RDS URL so schema locks and DDL never traverse the runtime pool. Keep both Secrets Manager ARNs wired to the ECS execution role.
- Production application logs use `backend/app/observability.py`: one privacy-safe JSON event per line with request correlation, plus CloudWatch EMF worker metrics. Do not add raw prompts, uploaded content, credentials, query strings, or arbitrary exception text to logs. See `docs/observability.md`.
- AWS hosted API and worker tasks may scale horizontally. Worker scaling uses `OldestQueuedAgeSeconds`; PostgreSQL claims must retain `SKIP LOCKED`, short claim transactions, expiring leases, and claim-token fencing. Never qualify multi-host SQLite/local/Chroma. See `docs/deployment.md`.

## Git And PRs

- Branch flow is `main <- dev <- task branch`. Never commit or push directly to `main` or `dev`.
- From a clean worktree, start a task with `git switch dev && git pull --ff-only origin dev && git switch -c <type>/SCRUM-XX-description`.
- Branches must match `^(feature|fix|chore|docs)/SCRUM-[0-9]+-[a-z0-9][a-z0-9._-]*$`.
- Update a task branch with `git fetch origin && git merge origin/dev`; never rebase or force-push.
- Use `type(scope): message` commits with type `feat`, `fix`, `docs`, `chore`, `test`, `refactor`, `ci`, or `style`. Keep formatting-only changes in a separate `style:` commit.
- A commit message is the subject line and nothing else. Do not add a body, description, rationale, or trailers, and never add `Co-Authored-By`, `Generated with`, or any other tool or agent attribution to commits or PRs. Explanation belongs in the PR description, not in git history.
- Stage intended paths explicitly. Do not use `git add .` except for an audited formatting-only sweep.
- PRs target `dev`; title them `SCRUM-XX: Description` and follow `.github/pull_request_template.md` exactly.
- PR `How to test` must list exact commands and expected results. Prefer `gh pr create --base dev ...` and `gh pr checks --watch`.
- Squash-merge with message `SCRUM-XX: description`, then delete the task branch.

## CI Contract

- Current `dev` job names are `Branch and PR policy`, `Repository quality`, `Backend quality and tests`, `Migration governance`, `PostgreSQL quality`, `Container quality`, `Infrastructure quality`, `Frontend quality and build`, and `Frontend end-to-end`. The last is `continue-on-error: true` while the browser suite proves itself; making it blocking is a ruleset change as well as a workflow change.
- Job names are referenced by dormant rulesets. Flag the corresponding ruleset update before renaming one.
- CI must verify, never modify: no `--fix`, generated changes, or auto-commits. Keep `permissions: contents: read`.
- Third-party Actions must remain pinned to immutable 40-character commit SHAs.
- Do not add checks for components absent from the checked-out repository.

## Security And Safety

- Never write or log secrets. Commit placeholders only in `.env.example`; add every new configuration variable there in the same PR (CI verifies all variables read by config are declared in `.env.example`).
- Passwords persist only as `password_hash`. Logs may identify filenames but must not print uploaded contents or credentials.
- Future AWS authentication must use GitHub OIDC/IAM roles, not stored long-lived keys.
- Ask before destructive operations. The sole pre-approved reset is `rm -rf data`, which removes only ignored runtime state.
- Use Windows Git Bash-compatible commands; the venv activation path is `.venv/Scripts/activate` (`.venv/bin/activate` on Linux).
